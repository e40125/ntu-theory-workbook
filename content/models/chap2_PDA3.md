# CFG to PDA: run the grammar as a stack of pending output

## The bridge: generating a string and checking a string can cooperate

A grammar chooses how to build output. A PDA can guess those grammar choices while checking them against the supplied input. Its stack means: **this is the sequence still owed by the current derivation**. The next owed symbol belongs on top, so we can deal with it first.

The deck's grammar is \(S\to aTb\mid b\), \(T\to Ta\mid\varepsilon\). S either produces a single `b`, or an `a`, then T's output, then `b`. T can produce any number of a's. So the language consists of `b` and all strings of one or more a's followed by one b.

The stack is the machine's to-do list, with the **next job on top**. Expanding a variable breaks a job into smaller jobs. Matching a terminal checks off finished output against the actual input. Don't let the notation blur those actions together: planning an `a` and reading an `a` are two different damn steps.

The stack changes jobs here. Instead of unpaid IOUs from earlier input, it stores the grammar’s future to-do list. The next job has to sit on top. That is why push order matters: shove the list on backward and the machine tries to print the sentence backward. Let’s make that ordering explicit.

## Round 1 — The stack becomes a to-do list for a derivation · pages 1–2

The theorem says a language is context-free exactly when some PDA recognizes it. This deck proves CFG→PDA. Start with a grammar and build a machine that guesses a derivation while checking its terminal output against the supplied input.

The source grammar is S→aTb|b and T→Ta|ε. T can make any number of a's: each use of T→Ta adds a pending a, and T→ε stops. Therefore S makes b, or one initial a followed by any number of additional a's and a final b. In compact notation its language is a*b. Recognizing that language directly is easier than the general conversion, but the slide deliberately demonstrates the conversion procedure.

## Round 2 — Why the right side gets pushed backward · pages 3–7

For S→aTb, the next input to check is a, then whatever T generates, then b. The stack must therefore have a on top, T underneath, and b underneath T. Push b first, then T, then a. If you push a first, b ends up on top and the machine tries to read the output backward. That ain't a harmless implementation detail.

Initialize with $ and then S. At the main loop, if the top is a variable, nondeterministically choose one of its productions and replace it by the right side. If the top is a terminal t, consume exactly input t and pop it. If only $ remains, remove it and go to the accepting state.

A course PDA transition pushes at most one symbol, so pushing a whole right side is shorthand for a chain through fresh helper states. Those helper states must have only the intended continuation; otherwise another rule could interrupt halfway through the push. Rule expansion consumes ε input. Terminal matching consumes real input. If you include only expansion arrows, you can generate a stack forever while never checking a single input symbol.

## Round 3 — Read the slide's aaaab trace as unfinished output · pages 8–9

After initializing S$, choose S→aTb and obtain top-left `aTb$`. Match the first a: unread input becomes `aaab`, stack `Tb$`. Expand T→Ta three times: `Tab$`, `Taab$`, `Taaab$`. Then choose T→ε, leaving `aaab$`. Match the remaining three a's and b one by one; only $ remains. Remove it, with no input left, and accept.

Notice the subtlety: while T keeps expanding, those extra a's wait **below** it. They are not consumed until T is removed. The stack represents future required output, not a bag of characters already seen. The old “stack counts previous zeros” example used the same data structure for a different purpose.

## Round 4 — Why guessing can't fabricate a wrong string · page 10

At main-loop checkpoints, the already-consumed input prefix followed by the pending stack string above $ is a sentential form derivable from S. A variable expansion applies a genuine production, preserving that statement. A terminal match shifts the first pending terminal into the consumed prefix without changing their concatenation.

If the machine accepts after consuming all input and exhausting pending work, the complete input was generated by the grammar. Conversely, choose a leftmost derivation of any grammar-generated string; the machine can choose the same productions and match its terminals, reaching acceptance. These are the two correctness directions.

A branch that reaches the accepting state with unread input does not accept that input. A branch that expands forever produces no finite accepting run. Neither invalidates the construction; the existence of a correct finite branch is what matters. Nonaccepting branches are not allowed to vote down the successful one.

## Reconnect the pieces in the worked model

Now put the mechanism back together. The worked model below revisits the key example and compresses the reasoning into something you can reconstruct.

## There are only two kinds of work

If the stack top is a **variable**, replace it using a grammar production. This consumes no input, because choosing how to produce a symbol is not the same as matching an actual symbol.

If the top is a **terminal**, it must equal the next input symbol. Consume that input symbol and pop the matching terminal. If they disagree, that branch has no matching move. A terminal cannot be expanded into something more convenient.

Initialize with S above a fresh bottom marker `$`. Finish when the pending work is exhausted, by removing `$` and entering accept. Input must also be fully consumed.

## A complete trace of `aaab`

Write the stack top first; omit `$` in this table only to make the pending work visible.

| Move | Unread input | Pending stack |
|---|---|---|
| initialize | `aaab` | S |
| choose S→aTb | `aaab` | aTb |
| match `a` | `aab` | Tb |
| choose T→Ta | `aab` | Tab |
| choose T→Ta | `aab` | Taab |
| choose T→ε | `aab` | aab |
| match `a` | `ab` | ab |
| match `a` | `b` | b |
| match `b` | ε | empty |

Now `$` can be removed and the run can accept. Notice how T→Ta adds a pending a **after** T. Expanding the variable repeatedly builds more work without consuming input; terminal matching pays it off afterward.

## Why pushes appear reversed on the diagram

To leave `aTb` top-first, physically push b first, then T, then a. The last pushed symbol is on top. That is a consequence of stack order, not a rule that reverses the generated language. If a diagram abbreviates a multi-symbol push, expand it into single pushes in that order using fresh intermediate states.

With a wrong production choice, the machine may get stuck. It can also keep choosing T→Ta forever. Such a branch does not accept. A finite successful derivation supplies a finite successful branch; existence of other bad branches doesn't invalidate it.

## Why the conversion is correct

After matching a prefix of the input, the stack records the ungenerated/unmatched remainder of a chosen leftmost derivation. Variable expansion changes that remainder exactly as a grammar step would. Terminal matching removes the next symbol only when it agrees with the input.

Thus a successful run describes a grammar derivation of the entire input. Conversely, a derivation of the input tells the PDA which productions to choose, giving a successful run. This is the two-way language-equality proof; tracing `aaab` alone is only an illustration.
